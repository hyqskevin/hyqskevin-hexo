## 二、Agent 底层原理详解

### 2.1 第 1-5 题:核心概念辨析

**1. Context Window 的核心作用是什么?**

- **答案:B** —— 限制单次对话中模型能处理的文本总长度
- **辨析**:A 错把"上下文窗口"和"长期记忆"混为一谈,后者需要向量库等外部设施。常见的误区是把 Context 当数据库用,实际上它的物理边界就是单次推理的 KV Cache。

**2. Session 与 Context 的本质区别?**

- **答案:A** —— Session 是完整交互周期可持久化,Context 是当前窗口文本会随滑动丢失
- **辨析**:这是一道"工作记忆 vs 长期记忆"科普题。Session 决定"会话还在不在",Context 决定"这次推理看得到哪些字"。

**3. CLAUDE.md 文件的主要作用?**

- **答案:A** —— 定义项目级系统提示词,写入代码规范和架构约束供 Agent 遵循
- **辨析**:这是 Agent 工程化最关键的一步。把规范写进文件 = 让 Agent"记住"你的项目要求,而不是每次都要在 Prompt 里复述。

**4. Hermes 的 `profiles` 字段设计目的?**

- **答案:C** —— 隔离不同环境的配置,每个 profile 有独立模型选择与工具集
- **辨析**:多环境(开发/测试/生产/家庭)是 Agent 配置的常见痛点,profile 机制允许同一个 config.yaml 描述多种部署形态。

**5. Workspace 的核心设计目的?**

- **答案:A** —— 隔离不同项目的文件和配置,防止 Skill 和 Memory 交叉污染
- **辨析**:当 Agent 同时服务多个项目,Workspace 是物理+逻辑双重隔离的容器,比"靠 Prompt 提示要小心"靠谱得多。

### 2.2 第 6-10 题:安全与架构

**6. Prompt Injection 的攻击本质?**

- **答案:C** —— 在用户输入中嵌入恶意指令,覆盖或绕过系统预设提示词
- **辨析**:这是 Web2 XSS 在 AI 时代的翻版。防御手段包括:输入清洗、指令优先级声明、输出过滤、敏感操作二次确认。

**7. 哪种机制能让 Agent 在"重启后"仍然记得用户偏好?**

- **答案:B** —— 持久化记忆,将偏好以向量形式存入外部数据库跨会话检索
- **辨析**:上下文学习是"短时记忆",持久化记忆才是"长期记忆"。两者协同,才能让 Agent 真正"懂你"。

**8. ReAct 范式的核心创新?**

- **答案:D** —— 让模型交替执行推理和工具调用,形成循环直到任务彻底完成
- **辨析**:ReAct = Reason + Act。Thought → Action → Observation → Thought 的循环,是 Agent 区别于"普通 LLM 调用"的标志性结构。

**9. System Prompt 的最佳实践?**

- **答案:B** —— 详细定义 Agent 角色、能力边界、输出格式和禁止行为等约束条件
- **辨析**:经验法则是"该写清楚的写清楚,该禁止的明确禁止"。模糊的 prompt = 模糊的输出。

**10. Tool Use 与 Function Calling 的关系?**

- **答案:B** —— Tool Use 是上层抽象概念,Function Calling 是具体的技术实现方式
- **辨析**:Anthropic 偏好说 Tool Use,OpenAI 偏好说 Function Calling,本质上是同一件事的两个视角。

### 2.3 第 11-15 题:推理与参数

**11. Orchestrator 的核心职责?**

- **答案:D** —— 管理多个 Agent 之间的任务分配调度、状态同步和冲突裁决
- **辨析**:单 Agent 时代不需要 Orchestrator,多 Agent 协作的核心就是它。常见实现:LangGraph、AutoGen、CrewAI。

**12. Chain-of-Thought 提示技术的主要作用?**

- **答案:C** —— 通过展示中间推理步骤来提升模型在复杂问题上的最终准确率
- **辨析**:CoT 的本质是"让模型有时间思考"。o1/R1 类推理模型把这个思路推到了极致——也付出了 token 成本的代价。

**13. Temperature 设置为 0.2 时模型会?**

- **答案:A** —— 倾向于输出更确定更一致的答案,随机性和创造性明显降低
- **辨析**:工程经验:事实型问答 T≈0,创意型生成 T=0.7-1.0,代码补全 T≤0.2。

**14. RAG 与 Fine-tuning 的核心差异?**

- **答案:D** —— RAG 从外部动态检索知识不改变模型,Fine-tuning 将知识固化到权重中
- **辨析**:这是 2025 年的共识选型逻辑——RAG 处理"知识更新",Fine-tuning 处理"行为对齐"。

**15. Agent"观察-思考-行动"循环中,"观察"主要获取?**

- **答案:D** —— 上一轮工具调用或环境交互返回的执行结果和外部反馈
- **辨析**:Observation 在 ReAct 循环里就是"反馈信号",让模型知道上一步走得对不对。

## 三、2025+ 新模型特性深度对比

### 16. Kimi K2.6 相比前代的核心升级

- **答案:A** —— 引入"长思考"模式以支持深度推理和对超长文档的复杂分析
- **辨析**:长思考是 2025 下半年的标配,不只是 Kimi,o 系列、R1、GLM-Think 都进入了这个赛道。

### 17. Claude 4 在代码能力上的主要突破

- **答案:B** —— 引入"扩展思考"模式,可在跨文件重构中深入理解整个代码架构
- **辨析**:"扩展思考"的意义不只在代码——它意味着模型愿意花更多 token 推理"为什么这么改",而不是机械执行命令。

### 18. GPT-5 的"原生多模态"特性

- **答案:A** —— 文本、图像、音频、视频在同一个模型内统一处理而非分别调用
- **辨析**:这条切的是"模型架构"层面,而不是"输入端扩展"。原生 = 一个权重搞定所有模态。

### 19. Claude Code 与 Cursor 在 IDE 集成上的核心区别

- **答案:A** —— Claude Code 是终端 CLI 工具通过命令行交互,Cursor 是完整的集成开发环境
- **辨析**:CLI vs GUI 不是好坏之分,看使用场景——CLI 适合自动化脚本和 CI/CD,GUI 适合沉浸式开发。

### 20. Gemini 2.5 Pro 的"1M token 上下文"主要意义

- **答案:B** —— 可一次性输入整本书或大型代码仓库进行分析,保持跨段落的长距离依赖
- **辨析**:超长上下文 ≠ 超长记忆。长上下文的成本是 cache 命中率和首字延迟,不是越多越好。

### 21. Claude Code 的"扩展思考"模式最适用场景

- **答案:B** —— 处理跨多个文件的复杂架构重构,需要深入理解模块间依赖关系
- **辨析**:扩展思考的本质是"花更多 token 换更高的思考深度",简单问题用它反而浪费时间和金钱。

### 22. 哪个场景最适合优先考虑国内模型?

- **答案:C** —— 涉及国内数据合规监管要求,且目标用户以中文母语者为主
- **辨析**:合规 + 中文语料 + 国内 CDN,这三条让国内模型(Kimi、文心、通义、豆包)成为必选。

### 23. 高频、低复杂度客服场景的成本最优组合

- **答案:C** —— 通义千问 2.5 或豆包 Pro,国内模型成本低且中文场景优化
- **辨析**:高频场景里"每千 token 几分钱"的差价会被放大万倍,选模型本质是选 TCO。

### 24. 哪个产品的核心定位是"搜索原生"?

- **答案:C** —— Perplexity
- **辨析**:Perplexity 走的是"AI 版搜索引擎"路线,聊天对话只是副产品,把"引文+结果"作为第一公民的产品。

### 25. 哪种做法最有效避免 Claude Code "跑偏"?

- **答案:C** —— 将项目规范写入 CLAUDE.md 文件,Claude Code 启动时自动加载遵循
- **辨析**:和其他工具对比,Codex 也有类似机制(AGENTS.md)。一次写好,胜过每次重申。

### 26. "Vibe Coding"在 2025 年的准确定位

- **答案:B** —— 适合快速原型验证和 MVP 探索,大型项目仍需人工架构设计兜底
- **辨析**:Vibe Coding 解决"从想法到 demo"的那段路,但生产级的架构、性能、稳定性仍然要工程师。

### 27. Codex CLI 在执行代码时的核心安全机制

- **答案:A** —— 每次运行前要求用户手动确认许可,且生成的代码在隔离沙箱中执行
- **辨析**:这是 AI 编程工具的安全底线——既给能力,也给"撤销键"。

### 28. Claude Code 与 Codex 在项目上下文理解上的主要差异

- **答案:A** —— Claude Code 通过 CLAUDE.md 读取项目规范,Codex 通过 AGENTS.md 获取上下文
- **辨析**:本质差异不大,文件命名和加载顺序才是重点。混用时注意规范冲突。

### 29. 哪个工具最适合非技术人员快速搭建 AI 应用?

- **答案:C** —— Coze / Dify —— 低代码平台,通过可视化拖拽和表单配置即可搭建应用
- **辨析**:低代码平台的边界是"业务原型 + 单部门工具",企业级系统仍需代码兜底。

### 30. "微调 vs 提示词工程"在 2025 年的最佳实践

- **答案:B** —— 先尝试提示词工程和 RAG 检索增强,仅在高频高稳定性场景才考虑微调
- **辨析**:微调是"重资产投入",ROI 只在高频高价值场景才划算。先轻后重是 2025 年的共识。

## 四、MCP、插件与生态配置

### 31. MCP 与 OpenAPI 规范的核心区别

- **答案:B** —— MCP 专为 AI Agent 设计强调上下文传递和工具发现,OpenAPI 是通用 HTTP 规范
- **辨析**:MCP 把 OpenAPI 的"我能调什么"扩展到了"AI 知道何时该调、怎么调、用什么数据调"。

### 32. 在 Hermes 中配置 MCP Server,`mcp_servers` 字段需要指定?

- **答案:A** —— 服务器进程的启动命令、运行所需的环境变量以及启动参数的配置
- **辨析**:字段名透露了它的本意——告诉 Agent "到哪里去拉起这个 MCP 服务"。

### 33. "Heartbeat" 在 Cron 任务中的核心作用

- **答案:C** —— 周期性检测任务进程是否存活,一旦发现异常退出就触发告警和重试
- **辨析**:Heartbeat 是分布式系统的"心跳",让监控体系能及时发现"任务假死"。

### 34. 哪种场景更适合"外部 IM Plugin"而非 MCP?

- **答案:B** —— 仅需在特定 IM 平台内收发文本消息,不涉及 Agent 调用外部工具的逻辑
- **辨析**:判断标准——要不要让 Agent 触发外部动作?要,用 MCP;只是文本互通,用 Plugin。

### 35. 在 Dify 中配置知识库,Chunk Size 的设置原则

- **答案:C** —— 根据文档类型和内容密度平衡取舍,太小丢语义,太大的话检索精度下降
- **辨析**:经验区间:技术文档 300-500,客服话术 200-400,法律条文 500-800。多做 Ragas 评测,比拍脑袋准。

### 36. 【多选】MCP 相对于传统 API 集成的优势

- **答案:A、B、C、E** —— 标准化工具发现 / 上下文传递 / 跨平台复用 / 本地和远程混合部署
- **辨析**:D 是反选项,MCP 的核心价值之一就是"一次开发,处处复用"。

### 37. 【多选】配置 Claude Code 时的关键文件

- **答案:A、B、C** —— CLAUDE.md / .env / settings.json
- **辨析**:D(E)虽然在多数项目存在,但和 Claude Code 的直接行为关系不大,属于干扰项。

### 38. 【多选】Agent 生态核心组件

- **答案:A、B、C、D、E** —— 全部正确
- **辨析**:MCP Server 是工具提供方,Cron 是调度,Heartbeat 是监控,IM Plugin 是入口,Vector DB 是记忆。少一个都不完整。

### 39. 【多选】OpenClaw 配置多 Agent 协作时关注点

- **答案:A、B、C、D** —— Skill / 路由 / Context / 冲突解决
- **辨析**:E 是反选项——统一密钥管理,而不是"每个 Agent 一把钥匙",那样泄密风险更高。

### 40. 【多选】生产级 Agent 部署必须考虑

- **答案:A、B、C、D、E** —— 全部正确
- **辨析**:这是经典的 SLI/SLO + 治理 全景图。任何缺失一项都会在生产环境里以事故形式被发现。

## 五、工作流设计

### 41. 【多选】搭建"早 8 点自动 AI 行业新闻摘要并推送企业微信"系统必需的组件

- **答案:A、B、C、D、E** —— Cron + 新闻源 + AI 摘要 + Webhook + 告警重试
- **辨析**:少告警重试一项,凌晨任务失败可能要等 24h 后才知道。

### 42. 【多选】多 Agent 协作的常见模式

- **答案:A、B、C、D** —— 串行 / 并行 / 评审 / 竞争
- **辨析**:E"随机模式"是反选项,生产环境不允许随机调度。

### 43. 【多选】"AI 写周报"工作流的质量保障措施

- **答案:A、B、C、D、E** —— Git 数据 / 过滤 / 人工审核 / 确认环节 / 版本可回退
- **辨析**:"完全自动化写周报"是一个常被高估的能力,人工兜底是必须的。

### 44. 【多选】低代码平台相比纯代码开发的优势

- **答案:A、B、C、E** —— 快速原型 / 可视化 / 内置最佳实践 / 多平台发布
- **辨析**:D 是反选项,低代码平台的边界恰是不能"做任何复杂系统"——那是 R&D 的领地。

### 45. 【多选】自动化工作流中可能导致系统风险的实践

- **答案:A、B、C、D、E** —— 过度自动化 / 无日志 / 成本失控 / 隐私泄露 / 无人工审核
- **辨析**:这五项是"生产事故的五种典型死法",全中即是"系统已经不可信"的标志。

## 六、综合场景与方案选型

### 46. 电商公司搭"AI 智能客服"最合理方案

- **答案:B** —— 大模型处理对话理解与情绪安抚,规则引擎处理标准化查询,RAG 接入订单数据,人工兜底合规终审
- **辨析**:这是 2025 年企业级客服的"四层混合架构"——大模型不可信的部分交给规则,RAG 补事实,人工兜底合规。

### 47. 开发者用 AI 辅助从零开发 SaaS,最合理工具链

- **答案:B** —— Cursor + Claude Code + Codex + GitHub + Vercel
- **辨析**:这道题考的是"工具链组合能力",而不是"单一最强模型"——A 偏执于不用 AI,C 偏执于只用外包,D 后端缺失。

### 48. "AI 辅助创作流水线"哪个环节最不适合完全自动化?

- **答案:D** —— 涉及品牌声誉风险和法律合规审查的最终内容审核与发布签字确认
- **辨析**:A/B/C 都是机器擅长的"信息整理+生成",D 是需要"主体责任"的环节,机器无法承担法律责任。

### 49. 成本敏感场景下最能降低总拥有成本的策略

- **答案:D** —— 按任务复杂度分层:简单任务用轻量模型,复杂任务用强模型,高频查询做缓存
- **辨析**:这是 LLM 工程化的核心思想——"模型规模 ≠ 业务效果",分层是降本主线。

### 50. 关于"AI 应用架构"最准确的说法

- **答案:B** —— 好的 AI 应用是模型选型、工程架构设计和业务场景理解的有机组合与协同优化
- **辨析**:A/C/D 各有偏废。AI 应用不是"模型说了算",也不是"工程万能",更不能"合规事后补救"。

## 七、常见易错点与延伸思考

### 7.1 三大典型易错区

- **Session ≠ Context**:很多新人把两者混用,直到第一次做"跨会话记忆"才发现需要持久层。
- **Tool Use 不是 Function Calling 替代品**:两者是抽象层与实现层的关系,不是二选一。
- **RAG 不替代 Fine-tuning**:很多团队做了半年 RAG,发现"行为对齐"问题才回头做微调,走了弯路。

### 7.2 三个值得长期追踪的方向

- 推理模型(Reasoning Models)与 Agent 的协作范式——o1/R1 之后,谁先跑通"思考成本可控"的 Agent?
- MCP 生态的标准化与商业化——会不会出现"MCP 商店"?
